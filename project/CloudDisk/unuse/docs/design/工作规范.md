# 代码规范

1. 标准库命名空间不能展开

2. 最外层命名空间为项目名称, 使用蛇形命名法

> 以 cloud-disk-apple 举例
> 蛇形命名: cloud_disk_apple
> 小驼峰: cloudDiskApple
> 大驼峰: CloudDiskApple

3. 第二层命名空间为缩写模块名称, 通用模块使用小驼峰, 服务模块使用大驼峰
    类名使用大驼峰, 私有函数/公有函数子方法使用小驼峰, 公有函数使用大驼峰, 成员变量使用蛇形(前面带_)
    命名空间、类、函数、变量的命名使用不过于长的意思匹配的英文单词
    文件名应当与该模块的名称相同(可以为命名空间名/类名+适当后缀)

4. 如非必须(性能优化等因素, 如使用 mmap 优化文件读取效率等类似场景), 请使用 C++ 标准库的方法实现而非 system call

5. 请记得在合适的地方使用: 
工厂模式: 所要实例化的目标类中的成员变量的实例化所需形参过多, 将该成员变量的实例化拿出来单独进行(一个类作为该变量的工厂, 有一个 static 的 Create 函数即可), 在目标类中存储该变量的智能指针(除此之外如果无法拿出来使用工厂&形参过多就要考虑单独拿出来一个 struct 充当形参列表的作用)
建造者模式: 所要实例化的目标类的成员变量过多, 并且成员变量的初始化顺序很重要(例如: 先初始化 A 再初始化 B), 将该类拆分为 Builder 类, 在 Builder 中依次调用各个成员变量的初始化函数
责任链模式: 需要执行线性的/流水线一样的操作, 一个一个调用函数过于麻烦, 将调用逻辑放在一个函数内通过逻辑判断 + 链式调用实现需求

6. 注释(中文即可, 标点请用英文): 请务必在合适的地方写注释, 不要写没用的注释, 包括但不限于复杂逻辑, 复杂形参列表的作用介绍, 私有成员变量的作用介绍, 函数的作用介绍...
   日志: 使用英文

7. 每一个小模块实现好后都要进行单元测试(设计测试用例、执行测试计划、测试通过请在该文档最上方用注释标注)

8.   目录结构: (为保证 clone 的目录结构完整, 在空目录下暂存了一个占位文件, 请在该目录下有文件前不要删除)
├─unuse(已弃用的模块, 不用管不用删)
├─docs
│  ├─design (相关文档)
│  └─pictures (项目所用图片 & 素材)
└─project
    ├─browser
    │  └─同server
    ├─client
    │  └─同server
    └─server
        ├─example
        │  └─基础组件使用样例
        ├─project
        │  ├─common (通用模块)
        │  ├─interface (proto 接口模块)
        │  └─其它微服务模块(gateway, use, file)
        └─test
            └─测试
每个微服务模块封装代码请为其单独建立目录
微服务功能实现代码在 source 目录下
example:
user/
├── dms
├── odb
├── operator
├── otp
└── soure

9.   代码编写与提交相关: 
正式开始项目后(前期准备工作全部完成后)所有开发人员需从 develop 分支上拉下自己的分支进行代码编写提交, 如果自己的模块完成编写需要提交合并需要先 merge develop 分支到自己的分支解决冲突后再在 gitee 工作台提交合并请求, 提交合并请求后需要等待评审人员进行代码评审, 评审通过后合并到 develop 分支, 若未通过代码评审则需要修改后重新提交合并请求
